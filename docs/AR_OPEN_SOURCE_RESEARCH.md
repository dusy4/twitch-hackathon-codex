# Ready AR stacks for RaidRift

Research date: 2026-10-29. Scope: Android phone, moving camera, actual skinned 3D characters anchored to sensed room surfaces, and live composited video for an existing streamer relay/OBS workflow. Headset passthrough, marker demos and ordinary 3D previews are different capabilities.

## Finding and decision

There are ready libraries. RaidRift already uses one: SceneView wraps ARCore tracking and Filament rendering. We should not write a SLAM tracker. The immediate failure is that our integrated viewport has not produced a usable tracked placement in the emulator, while a separate direct-ARCore diagnostic on the same virtual table detected four tracked horizontal planes and valid hit tests. This establishes an integration/performance problem to investigate, not that ARCore or the environment is inherently incapable of detecting surfaces. It does not establish physical-phone performance.

First test SceneView's documented `RenderQuality.Performance`, ARCore's stock camera configuration (`sessionCameraConfig = null`), and inexpensive light estimation. SceneView deliberately defaults to the highest-resolution back-camera configuration for full-resolution recordings; that differs from the direct diagnostic. Its performance preset is explicitly intended for constrained devices and AR camera feeds. These are available library features, not a new engine. [Current API guide](https://sceneview.github.io/llms.txt), [pinned ARSceneView source](https://github.com/sceneview/sceneview/blob/v4.62.0/arsceneview/src/main/java/io/github/sceneview/ar/ARSceneView.kt).

In parallel with this narrow comparison, build Google's official `hello_ar_java` sample as an independent camera + plane + 3D placement reference. If the stock reference works and SceneView's minimal configuration still does not, compare alternative renderers before migrating the product. Viro's maintained packaged route is ViroReact; its standalone Java module has an important build caveat below. No candidate is accepted on README claims alone. [Google quickstart](https://developers.google.com/ar/develop/java/quickstart).

## Why switching engines is not yet the diagnosis

Google documents low VIO frequency as a sign of CPU starvation. Our integrated run logged about 2.3 Hz VIO and very low unique camera-image cadence. Reducing the viewport and changing HDR to ambient estimation alone did not resolve placement. The direct diagnostic used disabled depth/light estimation and ARCore's default camera config, without Filament or the scene integration. Those differences should be isolated before choosing a rewrite. [Official performance guidance](https://developers.google.com/ar/develop/performance).

Upstream SceneView's sample QA issue provides useful defects and reproducible setup work, but its 60 FPS figure concerns a non-AR model viewer. Its AR rows include launch-only/replay checks and explicitly identify device-only gaps. It is not proof that our software-rendered x86 phone emulator should deliver 60 FPS tracked AR. [Upstream QA issue and scope](https://github.com/sceneview/sceneview/issues/2344).

For live streaming, the chosen renderer must produce **one composed camera + character surface** for the existing H.264 encoder. We must retain explicit microphone/camera consent, authoritative actor updates, bounded reconnect, pause/revoke clearing and existing SRT/RTMPS relay compatibility. A plane-placement demo or a local MP4 recording alone cannot pass that requirement.

## Verification gates

Source-level capture check: ViroCore 3.0.3's `ViroMediaRecorder.startRecordingAsync` configures Android MediaRecorder and an internal EGL recording surface for a local MP4. It checks audio/recording permissions. Its native EGL bind/swap methods are internal callbacks, not an advertised arbitrary encoder-surface API. A migration would therefore require an explicit live-surface adapter and video-only consent handling; it is not a drop-in replacement for our working RootEncoder/Filament mirror. This narrows the initial recommendation to the existing SceneView integration while retaining ViroCore as a renderer benchmark. [Pinned recording source](https://github.com/ReactVision/virocore/blob/v3.0.3/android/sharedCode/src/main/java/com/viro/core/ViroMediaRecorder.java), [pinned native AR view](https://github.com/ReactVision/virocore/blob/v3.0.3/android/sharedCode/src/main/java/com/viro/core/ViroViewARCore.java).

Source-level packaging check: the 3.0.3 `android/virocore/build.gradle` ends by disabling both `assembleRelease` and `assembleDebug` for the standalone module and says to use `viroreact`. Maven publication blocks there are commented out. Its module ABI filters list ARM64/ARMv7, while shared source has x86_64 configuration. The release has no attached AAR assets in the GitHub release API; official npm metadata does expose `@reactvision/react-viro@3.0.3`. Consequently, a Java API in the source tree is not evidence of a currently published standalone Kotlin/Java drop-in. This materially reduces its advantage over the already integrated SceneView stack. [Pinned module build](https://github.com/ReactVision/virocore/blob/v3.0.3/android/virocore/build.gradle), [release distribution](https://github.com/ReactVision/virocore/releases/tag/v3.0.3).

1. Reference sample: actual camera image, detected horizontal plane, hit-test-created anchor and visible 3D object; move the virtual/physical camera and inspect parallax. Record environment/version and scope.
2. Candidate renderer: same scene and movement, our skinned GLB and animation, no synthetic plane injection. Measure unique camera timestamps separately from UI/render updates.
3. RaidRift: paired server actor actions remain individual and appear on sensed support, survive camera movement appropriately, and hide/stop on tracking loss.
4. Live composition: decode the actual native camera + character stream in OBS, measure action latency and audio, interrupt and restore the relay, and verify stale frames clear after stop/pause/revoke.
5. Physical phone: sustained camera motion, drift, frame rate, heat/battery, cellular transitions and microphone/A/V sync. Emulator success cannot pass this gate.

## Executed comparison, not library marketing

- Built and installed Google's `hello_ar_java` from source commit `204ddfd1715eb0cb775bf7528c9aee9d93cd4d4a`. Its Java/sample assets are unchanged; the local benchmark copy uses cached AGP 9.4.1 instead of 9.3.0 after a Maven TLS download failure. Actual screenshots show its camera feed and feature points. Initial one-core scan remained “Searching for surfaces”; no reference-object placement pass is claimed.
- Built/installed RaidRift `901e1ded…` with the ready SceneView Performance preset, stock camera config and ambient estimation. One-core tracking still failed to provide usable placement. The guest exposed only CPU 0; a sampled camera-active `top` reported about 73% IRQ time. This is an observed lab constraint, not proof of a specific engine defect.
- Restarted the same VM's emulator with two guest cores. RaidRift intermittently reported four tracked horizontal planes. An automated tester tapped the actual viewport in response to observed tracking/plane logs; the app's real `frame.hitTest` returned a Plane and the anchor-created Reset control appeared. No planes or hit results were injected. Tracking continued to drop frequently at about 0–2 unique camera images per second. **Stable visible character placement and AR streaming remain unpassed.** Logs/screenshots: `artifacts/android-sceneview-two-core-ar.txt`, `artifacts/android-sceneview-tap-watch.png`.
- The next build additionally gates the depth collider on actual ARCore depth support and hides the plane visualization after anchoring. This removes unsupported acquisition work and grid rendering; it does not disable plane tracking. Nineteen native tests and lint pass. Runtime performance is measured separately rather than inferred from compilation.
- The depth-gated run still failed to provide a supported visible character in its observation window. Google's reference was also rerun on two cores, then rebuilt with disabled HDR plus diagnostic counters. That modified run showed intermittent camera tracking but zero horizontal planes and zero anchors in the captured interval. Its exact reproducible patch and scope are in `tests/android-arcore-reference/`; this does not prove another renderer will fix the lab limitation.

These results justify keeping the ready SceneView stack for the next measured comparison, while retaining ViroCore as a credible renderer alternative. They do not justify claiming the product's physical AR gate is complete.

## Retrieval scope

Used Exa discovery queries across native Android, Unity, Godot, Babylon, Viro, browser AR and compositor support; Firecrawl searches and primary-page reads; then local checkout of Google's source for an executable baseline. Read official repositories, release notes, license files, SDK guidance and relevant maintainer issues. Search excerpts were discovery leads, not a claim to have run every library. One legacy Viro documentation host failed TLS, and two guessed current raw Java paths returned 404; neither is treated as usable current API evidence. The current Viro release and repository are the maintained sources. No library is marked operationally accepted without its own test result.
